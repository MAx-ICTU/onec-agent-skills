# Различающие проверки

Читай только относящийся к задаче пункт. Имена ниже обозначают условную структуру, а не метаданные проекта пользователя.

## СрезПоследних

Сначала выпиши все измерения — они определяют независимые серии записей. Для независимого периодического регистра с измерением `Товар`, реквизитом `Источник` и ресурсом `Цена` последние записи на дату могут иметь другой источник, чем более ранние.

`СрезПоследних(&Дата)` с последующим `ГДЕ Источник = &Источник` отвечает «последние цены в целом, если их источник подходит». `СрезПоследних(&Дата, Источник = &Источник)` отвечает «последние среди записей подходящего источника». Для товара с ранней ручной и поздней импортной ценой результаты различны. Если `Источник` — дополнительное измерение, это уже другая структура серий: вывод прежнего контрпримера нельзя переносить автоматически.

Проверка: ранняя подходящая + поздняя неподходящая; только подходящая; ни одной записи; дата до первой записи и точно на границе периода. Для подчинённого регистратору регистра, активности записей и режимов совместимости уточни применимую документацию; этот упрощённый независимый регистр не покрывает эти варианты.

## Размножение строк

Одна продажа на 100 и две подходящие метки справа дают две строки по 100. Если нужно только наличие метки, используй проверку вхождения/существования или уникальный набор ключей справа. Если нужны суммы двух табличных частей, агрегируй каждую до согласованного полного ключа **до** соединения; проверь, что это соответствует задаче.

Контроль против ложного исправления: две реальные продажи по 100 должны дать 200. `СУММА(РАЗЛИЧНЫЕ Сумма)` даст 100 и скроет данные. Неполный ключ с пропущенным складом/организацией/видом цены — отдельная возможная причина; не добавляй эти поля, если их нет в реальных метаданных.

## Левое соединение и NULL

Для строки без соответствия поля справа равны `NULL`; обычное сравнение с ними не даёт истинного условия отбора. `ГДЕ Правая.Активна = ИСТИНА` удаляет такую строку. Если задача — сохранить все товары и присоединить только активные записи, условие обычно относится к `ПО` (либо к заранее отобранному правому набору). Если нужны только товары с активной записью, исходный отбор может быть верен.

Замена на `ГДЕ Активна = ИСТИНА ИЛИ Ключ ЕСТЬ NULL` не равноценна переносу в `ПО`: товар с существующей, но неактивной записью также должен остаться в варианте «все товары». Проверь три случая: активная, неактивная, отсутствующая запись. Несколько подходящих строк справа остаются источником размножения и после переноса условия.

## Запрос в цикле

При исходных строках `(1, A), (2, B), (3, A), (4, C)` пакетное чтение по ключам может вернуть только `A` и `B`. Нужно восстановить четыре результата, включая повтор `A` и отсутствие `C`. Варианты: соединить временную таблицу исходных строк с уникальным набором результата либо построить соответствие по **полному ключу** и повторно обойти исходные строки.

Если итерации отличаются датой, складом или организацией, один ключ товара недостаточен. Если между итерациями выполнялась запись или цены могли изменяться и контракт требует видеть каждое изменение, пакетирование может быть неэквивалентным. Пустой список, размер пакета, ограничения памяти, права и повторяющиеся ключи проверяются отдельно.

Для строкового ключа отдельно проверь регистр символов и завершающие пробелы. [Developer Guide 8.3.27, §8.4.18.3 Value comparison rules](https://1c-dn.com/library/tutorials/1c_enterprise_developer_guide_8_3_27/#8-4-18-conditions-in-query-language) описывает сравнение строк запросом без учёта регистра и завершающих пробелов; его нельзя автоматически заменить поиском ключа в `Соответствие`. Инженерный вариант — выполнить сопоставление товаров в запросе, вернуть идентификатор исходной строки и заполнять строки по нему. Не объявляй модель с точным равенством строк Python проверкой этих правил 1С.

Примеры и рубрики в репозитории служат проверяющему; для применения установленного скилла они не обязательны. Технические ссылки и статус их применимости приведены в `SKILL.md`.
