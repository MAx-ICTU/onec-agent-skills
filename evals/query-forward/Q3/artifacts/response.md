# Результат ревью

Исходный запрос не соответствует задаче: условие активности в `ГДЕ` исключает товары с неактивным разрешением и товары без записи разрешения. Минимальное исправление — перенести это условие в `ПО` левого соединения. Цель изменения — исправить ошибочный результат, а не сохранить результат исходной версии.

Применён скилл `onec-query-review`, включая раздел «Левое соединение и NULL» предоставленного `skill/references/query-pitfalls.md`. Использованы только разрешённые входные файлы; интернет и внешние приложения не использовались.

## Контракт и кардинальность

Одна строка результата — один элемент справочника `УчебныеТовары`. Нужно вернуть все товары; комментарий присоединяется только из активного разрешения. При отсутствии активного разрешения поле комментария остаётся `NULL`. Замена на пустую строку задачей не задана.

Регистр независимый и непериодический, его единственное измерение — `Товар`; на товар допускается не более одной записи. Соединение по ссылке товара использует полный ключ. Поэтому каждому товару соответствует ноль или одна строка регистра, размножения строк в данном контракте нет. `РАЗЛИЧНЫЕ`, группировка и дополнительные поля ключа не нужны. Порядок результата не задан и не проверяется.

## Доказанное расхождение

После исходного соединения A связан с активной записью, B — с неактивной, а у C поля правой стороны равны `NULL`. Затем `ГДЕ Разрешения.Активна = ИСТИНА` оставляет только A: для B условие ложно, для C сравнение с `NULL` не даёт истинного условия отбора.

Результаты ниже выведены статическим разбором и воспроизведены Python-моделью; это не вывод выполнения 1С:

| Товар | Исходный запрос | Исправленный запрос |
|---|---|---|
| A | «допущен» | «допущен» |
| B | строки нет | `NULL` |
| C | строки нет | `NULL` |

Достаточный минимальный контрпример — единственный товар без записи разрешения: исходный запрос возвращает ноль строк вместо одной. Отдельный различающий случай — единственный товар с неактивным разрешением: он также должен сохраниться без комментария.

Условие `ГДЕ Разрешения.Активна = ИСТИНА ИЛИ Разрешения.Товар ЕСТЬ NULL` не исправляет задачу: B уже сопоставлен с существующей неактивной записью, поэтому его ключ не `NULL` и он по-прежнему исключается. На заданных данных модель этого варианта возвращает A и C, теряя B.

## Минимальное решение

```bsl
ВЫБРАТЬ
    Товары.Ссылка КАК Товар,
    Разрешения.Комментарий
ИЗ
    Справочник.УчебныеТовары КАК Товары
        ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.УчебныеРазрешения КАК Разрешения
        ПО Товары.Ссылка = Разрешения.Товар
            И Разрешения.Активна = ИСТИНА
```

Теперь неактивная запись B не удовлетворяет условию соединения. Левое соединение сохраняет B с полями правой стороны `NULL`, как и C без записи. A получает комментарий активной записи. Активное разрешение с пустым комментарием вернёт пустую строку, которая отличается от `NULL`; это различие сохраняется.

Используемые в `data.json` A, B, C — обозначения ссылок. В запрос не добавляются строковые сравнения с этими именами. `NULL`, пустая ссылка и `Неопределено` не подменяют друг друга.

## Фактически выполненные проверки

Сохранённый `check_model.py` выполнен доступным Python через сохранённый `run_checks.py`, без сторонних пакетов. `checks.txt` содержит точный исполнявшийся argv дочернего процесса, рабочую директорию, настоящий stdout/stderr и exit code `0`; stderr пуст.

1. Статическая проверка нормализованного текста установила, что `proposed.query` отличается от `before.query` только переносом условия активности из `ГДЕ` в `ПО` с добавлением `И`.
2. На исходном `data.json` модель дала одну строку для исходного запроса и три требуемые строки для исправленного. Результат сопоставлен с независимой спецификацией «для каждого товара взять комментарий единственной активной записи либо NULL» по составу строк, значениям и кратности, без требования порядка.
3. На тех же данных проверен ошибочный вариант `ГДЕ ... ИЛИ ключ ЕСТЬ NULL`: он теряет B.
4. Прошли семь дополнительных наборов: пустой справочник; несколько товаров без разрешений; одно активное разрешение; одно неактивное; активное с пустым комментарием; неактивное с пустым комментарием; несколько активных разрешений разных товаров с одинаковыми комментариями. Проверялись значения, число строк и кратность каждого ключа.
5. Прошли все 125 сочетаний пяти состояний для трёх товаров: записи нет, неактивная с пустым/непустым комментарием, активная с пустым/непустым комментарием.

Модель реализует обычное левое соединение с указанным размещением условия и представлением `NULL` через Python `None`. Она не является парсером или исполнителем языка запросов 1С. Текстовая проверка связывает модель только с точными формами исходного и предлагаемого запросов. Перебор конечного набора не является проверкой на всех возможных данных или всех версиях платформы. Несколько разрешений одного товара не моделировались как допустимые данные: это противоречит заданному ограничению. Несколько совпадений на один товар потребовали бы нового контракта кардинальности.

## Невыполненные проверки и подготовленная процедура

1С, синтакс-помощник и СУБД для задания недоступны; версия платформы и режим совместимости не заданы. Компиляция запроса, выполнение в 1С, фактические типы значений результата, план и время выполнения не проверены. Ни эквивалентность для всех данных, ни ускорение не заявляются. Сведений задачи достаточно для выявления ошибки; дополнительные неизвестные поля метаданных не предполагаются.

Подготовленная, но не выполненная процедура для тестовой базы:

1. Зафиксировать версию платформы, совместимость, СУБД и роль пользователя. Проверить заданные типы и ограничение единственной записи на товар.
2. Создать реальные ссылки A, B, C и записи разрешений A/Истина/«допущен», B/Ложь/«закрыт»; у C записи нет. При наличии других товаров в базе учитывать их в ожидаемом полном наборе либо использовать изолированную учебную базу.
3. Выполнить исходный и исправленный тексты в консоли запросов. Убедиться, что исправленный возвращает по одной строке для всех товаров, у A комментарий «допущен», у B и C именно `NULL`, а «закрыт» не возвращается. Проверять исходные значения программно или средствами консоли, чтобы отображение пустой ячейки не скрыло отличие `NULL` от пустой строки.
4. Повторить случаи отсутствия разрешений, неактивной записи, активной записи с пустым комментарием и нескольких активных записей разных товаров с одинаковым комментарием. Сравнивать ссылки, значения и кратность строк, а не порядок или только общее количество.
5. Если потребуется оценка производительности, собрать планы и повторные замеры в одинаковых условиях: те же параметры, объём и распределение данных, роль, состояние кеша. Исходный ошибочный запрос возвращает меньше строк, поэтому его время не доказывает эффективность решения требуемой задачи. Сравнивать корректные варианты, например условие в `ПО` и предварительно отобранный правый набор, и отдельно учитывать различия объёма результата. Индексы и процент ускорения по виду текста не назначаются.

Файлы результата: `proposed.query`, `response.md`, `check_model.py`, `run_checks.py`, `checks.txt` в разрешённой папке `Q3/artifacts`.
