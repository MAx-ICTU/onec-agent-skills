Предлагаю заменить запрос внутри цикла одним выполнением пакета: перенести идентификаторы и товары исходных строк во временную таблицу, соединить её с регистром и записать результат в исходные строки по числовому идентификатору. Применён локальный скилл onec-query-review из предоставленной папки input/skill.

Цель — сохранить результат исходной процедуры на успешном пути. В исходнике нет доказанной ошибки результата при условиях задания: для каждой строки он правильно различает найденную цену, в том числе нулевую, и отсутствие цены. Проблема стоимости — N вызовов Выполнить() для N строк, включая повторные чтения одного товара.

Контракт: одна выходная строка на каждую исходную строку, с тем же идентификатором, товаром и положением в ТаблицаЗначений. Цена и ЕстьЦена всегда заменяются. Для найденной записи ЕстьЦена = Истина и Цена равна ресурсу; для отсутствующей — Ложь и 0. Старые значения этих колонок не участвуют в расчёте.

Полное предлагаемое решение также сохранено отдельно в proposed.bsl:

```bsl
// Серверный общий модуль. Условия задачи: фиксированные данные,
// уникальные идентификаторы строк и не более одной цены на товар.
Процедура ЗаполнитьЦены(Строки) Экспорт

    Если Строки.Количество() = 0 Тогда
        Возврат;
    КонецЕсли;

    СтрокиПоИдентификатору = Новый Соответствие;
    Для Каждого СтрокаДанных Из Строки Цикл
        СтрокиПоИдентификатору.Вставить(
            СтрокаДанных.ИдентификаторСтроки, СтрокаДанных);
    КонецЦикла;

    Запрос = Новый Запрос;
    Запрос.Текст =
        "ВЫБРАТЬ
        |    ИсходныеСтроки.ИдентификаторСтроки КАК ИдентификаторСтроки,
        |    ИсходныеСтроки.Товар КАК Товар
        |ПОМЕСТИТЬ ВТИсходныеСтроки
        |ИЗ
        |    &ИсходныеСтроки КАК ИсходныеСтроки
        |;
        |
        |ВЫБРАТЬ
        |    ИсходныеСтроки.ИдентификаторСтроки КАК ИдентификаторСтроки,
        |    ЕСТЬNULL(Цены.Цена, 0) КАК Цена,
        |    ВЫБОР
        |        КОГДА Цены.Товар ЕСТЬ NULL ТОГДА ЛОЖЬ
        |        ИНАЧЕ ИСТИНА
        |    КОНЕЦ КАК ЕстьЦена
        |ИЗ
        |    ВТИсходныеСтроки КАК ИсходныеСтроки
        |        ЛЕВОЕ СОЕДИНЕНИЕ
        |            РегистрСведений.УчебныеФиксированныеЦены КАК Цены
        |        ПО ИсходныеСтроки.Товар = Цены.Товар";
    Запрос.УстановитьПараметр("ИсходныеСтроки", Строки);

    РезультатыПакета = Запрос.ВыполнитьПакет();
    Выборка = РезультатыПакета[1].Выбрать();
    Пока Выборка.Следующий() Цикл
        СтрокаДанных = СтрокиПоИдентификатору.Получить(
            Выборка.ИдентификаторСтроки);
        СтрокаДанных.Цена = Выборка.Цена;
        СтрокаДанных.ЕстьЦена = Выборка.ЕстьЦена;
    КонецЦикла;

КонецПроцедуры
```

Временная таблица содержит N строк: повторяющиеся товары сохраняются вместе с разными идентификаторами. По заданному полному ключу регистра Товар справа подходит не более одной записи. Поэтому левое соединение даёт ровно N строк: одну с ценой либо одну с NULL справа для каждой исходной строки. Условия на правую таблицу в ГДЕ нет, строки без цены сохраняются. Для проверки наличия используется NULL в ключе правой стороны; нулевая цена и пустая строка товара не означают отсутствие записи. Ресурс Число не содержит NULL в найденной записи, поэтому ЕСТЬNULL задаёт 0 только для отсутствующего соответствия.

Соответствие использует уникальный числовой ИдентификаторСтроки и хранит сами исходные строки. Процедура не удаляет, не добавляет и не сортирует строки. Порядок выборки запроса не задан и для заполнения несущественен. УПОРЯДОЧИТЬ ПО не требуется: значимый порядок остаётся у исходной ТаблицаЗначений.

Сопоставление Товар выполняется оператором равенства в запросе, как в исходной процедуре. Подмена его поиском строкового ключа в Соответствие могла бы изменить поведение для регистра символов и завершающих пробелов. В предложении товары не нормализуются в BSL. Приведённая в скилле семантика сравнения строк не проверена здесь на конкретной версии платформы; её проверка включена в процедуру для тестовой базы ниже.

Условия сохранения поведения следуют из задания: типизированная ТаблицаЗначений с указанными колонками, уникальные числовые идентификаторы, полный ключ Товар и не более одной соответствующей цены, корректные входы и разрешённое чтение в том же серверном контексте. Цены и видимость записей постоянны, между итерациями нет значимых записей. Других параметров итерации в исходнике нет: дата, склад, организация и срез не добавляются. Общий модуль используется на сервере; клиентское выполнение не требуется. При изменении данных, прав или границ транзакций между чтениями единое чтение требует нового анализа. Частичное заполнение при исключении может отличаться и исключено из контракта.

Для data.json итог в исходном порядке:

| ИдентификаторСтроки | Товар | Цена | ЕстьЦена |
| --- | --- | ---: | --- |
| 1 | A | 10 | Истина |
| 2 | B | 20 | Истина |
| 3 | A | 10 | Истина |
| 4 | C | 0 | Ложь |
| 5 | Z | 0 | Истина |

Простой запрос цен с В (&Список) сам по себе вернул бы лишь A, B, Z — три записи вместо пяти результатов исходных строк. Он не восстанавливает второй A и отсутствующий C. Это контрпример неполному варианту пакетирования, а не ошибка before.bsl.

По статическому разбору для непустой таблицы вместо N вызовов Выполнить() выполняется один ВыполнитьПакет(). В нём два оператора: создание временной таблицы и итоговое чтение. Это не утверждение об одном SQL-запросе, одном сетевом обмене или одном обращении СУБД. По числу операторов пакет содержит 2 вместо N; при N = 1 их больше, при N = 2 одинаково, при N > 2 меньше. Для пустой таблицы обе версии не выполняют запросов. На примере N = 5 анализ даёт 5 вызовов исходника против 1 вызова пакета; это расчёт по тексту, не измерение платформы.

Ожидается уменьшение затрат на многократный запуск запроса при заметном N. Дополнительная стоимость — временная таблица из N строк, результат из N строк и соответствие из N ссылок на исходные строки. При малом N пакет может оказаться дороже. Реальное ускорение, число операций СУБД, использование индекса регистра и план не измерялись. Конкретный индекс, разбиение на пакеты и размер пакета без объёмов и замеров не выбирались.

Фактически выполнены следующие проверки без 1С:

- Статически прослежены гранулярность, полный ключ, обработка NULL, запись обеих выходных колонок, сохранение объектов строк и их порядка. Дополнительные текстовые assert в скрипте проверили наличие конструкции пакета, левого соединения, проверки NULL, заполнения по идентификатору и ветки пустого входа; это не синтаксический анализатор BSL.
- Запущен сохранённый check_model.py, использующий только стандартную библиотеку Python. Две независимые по структуре модели сравнивают последовательные поиски и левое соединение с обратным порядком выдачи и заполнением по идентификатору. Основная модель использует точное равенство Python.
- Проверены данные задания с явно заданным ожидаемым результатом, семь отдельных наборов: пустой вход, одна найденная цена, одна отсутствующая, найденный ноль, все отсутствуют, повтор товара и непоследовательные идентификаторы, пустой строковый товар. Исходные Цена/ЕстьЦена заранее содержат посторонние значения.
- Полный перебор 3267 конечных наборов: длина строк 0–4, товары A/B/C, для каждого товара отсутствие цены либо цена 0/10. Сравнивались все строки, значения и порядок.
- Дополнительно проверена иллюстративная ASCII-модель равенства без учёта регистра и завершающих пробелов. Она показала сохранение результата при заполнении по идентификатору и расхождение с наивным точным строковым словарём. Этот самостоятельно заданный предикат не подтверждает правила строкового сравнения 1С, особенности Unicode или СУБД.

Скрипт завершился с exit code 0; stderr пуст; stdout заканчивается ALL MODEL CHECKS PASSED. Точный выполненный скрипт находится в check_model.py. Команда, фактические stdout/stderr и код завершения сохранены в checks.txt; отдельно оставлены stdout.txt и stderr.txt. Перезапуск после уточнения подписи аналитического числа вызовов также завершился с кодом 0; checks.txt содержит итоговый запуск текущего скрипта.

Две подходящие цены на один товар нарушают заданный контракт регистра и в модель допустимых данных не включены: при таком изменении структуры левое соединение размножало бы исходные строки. Несколько исходных строк одного товара проверены отдельно и допустимы. Перебор конечной модели не доказывает эквивалентность для всех возможных данных 1С.

Платформенная процедура подготовлена, но не выполнена:

1. На тестовой базе с заданными метаданными сохранить исходную и предложенную процедуры под разными именами в серверном общем модуле. Проверить BSL и текст пакета средствами фактической версии платформы; отдельно проверить источник &ИсходныеСтроки, создание временной таблицы, ВыполнитьПакет() и получение второго результата по индексу 1. Здесь платформы и синтакс-помощника нет, компиляция не подтверждена.
2. Для каждого набора создать две независимые копии типизированной ТаблицаЗначений с одинаковыми прежними значениями Цена/ЕстьЦена. Запустить обе процедуры без изменения регистра и прав между ними. Сверить количество, последовательность идентификаторов и товаров, а также Цена/ЕстьЦена для каждой исходной строки.
3. Повторить данные задания и пограничные наборы из модели. Добавить на платформе варианты a/A и завершающих пробелов, включая пустую строку, с одной допустимой записью регистра на соответствующий товар. Проверить, что исходный параметрический отбор и соединение дают одинаковые соответствия. Испытать большие корректные входы и разрешённые роли. Ошибки чтения и конкуренцию учитывать отдельно от заданной эквивалентности успешного пути.
4. Только после сверки результата измерить обе версии на одинаковых данных, сервере, роли и условиях кеша, с повторными прогонами. Зафиксировать версию, совместимость, СУБД, N и число разных товаров, время процедуры, память, операции по журналу/трассировке и план на целевой СУБД. Это установит эффект временной таблицы, пригодность индекса и целесообразность пакетирования для малых и больших N.
