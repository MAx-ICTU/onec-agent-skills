Причина завышения установлена: соединение по товару размножает реальные строки продаж на число активных меток. Минимальное исправление — заменить соединение проверкой вхождения товара в подзапрос активных меток. На предоставленных данных требуемая сумма — **200**; модель исходного запроса даёт **400**.

Применён скилл `onec-query-review`, включая пункт «Размножение строк» из предоставленного `skill/references/query-pitfalls.md`. Использованы только разрешённые входные файлы и собственные артефакты задания; входные файлы не изменены.

Контракт: требуется одна итоговая сумма по реальным строкам табличной части выбранного документа, товар которых имеет хотя бы одну активную метку. Идентификатор реальной строки — `(Ссылка, НомерСтроки)`; одинаковые товары и суммы в разных строках должны учитываться отдельно. Все строки предоставленного JSON принадлежат выбранному документу. Порядок результата не задан.

У регистра уникален полный ключ `(Товар, Метка)`. Соединение использует только `Товар`, поэтому справа для одной строки продажи допустимо несколько соответствий. Для каждой продажи с суммой s и числом активных меток k исходный запрос вносит s × k, тогда как контракт требует s при k > 0 и отсутствие вклада при k = 0. Это доказанная ошибка кардинальности, а не предположение о неизвестных метаданных.

Минимальный контрпример: одна продажа A на 100 и две активные метки A дают в исходном соединении две строки по 100; по контракту нужна сумма 100. В предоставленных данных:

| Номер строки продажи | Товар | Сумма | Активных меток | Строк после соединения | Вклад исходного запроса | Требуемый вклад |
|---|---|---:|---:|---:|---:|---:|
| 1 | A | 100 | 2 | 2 | 200 | 100 |
| 2 | A | 100 | 2 | 2 | 200 | 100 |
| 3 | B | 50 | 0 | 0 | 0 | 0 |
| Итого | | | | 4 | 400 | 200 |

Предлагаемый запрос также сохранён отдельно в `proposed.query`:

```bsl
ВЫБРАТЬ
    СУММА(Продажи.Сумма) КАК Сумма
ИЗ
    Документ.УчебнаяПродажа.Товары КАК Продажи
ГДЕ
    Продажи.Ссылка = &Документ
    И Продажи.Товар В (
        ВЫБРАТЬ
            Метки.Товар
        ИЗ
            РегистрСведений.УчебныеМетки КАК Метки
        ГДЕ
            Метки.Активна = ИСТИНА
    )
```

Цель изменения — исправить ошибочный результат; равенство со старой суммой не является критерием успеха. Предикат вхождения проверяет наличие товара среди активных меток и сохраняет каждую исходную строку продажи один раз. Повторение товара в подзапросе не размножает внешние строки, поэтому `РАЗЛИЧНЫЕ` внутри подзапроса не требуется. Отбор по `&Документ` сохранён. Поля метки в результате не нужны.

`СУММА(РАЗЛИЧНЫЕ Продажи.Сумма)` ошибочна: две реальные продажи по 100 должны дать 200, а такой вариант даст 100. Удаление дублей по `(Товар, Сумма)` также потеряет одну реальную продажу. `РАЗЛИЧНЫЕ` над единственной итоговой агрегатной строкой не исправит уже вычисленные 400. Перенос условия активности из `ГДЕ` в `ПО` внутреннего соединения также сохранит размножение.

Фактически выполнены статический разбор ключей, условий отбора и гранулярности и запуск модели на стандартной библиотеке Python. Точный исполнявшийся скрипт сохранён в `verify.py`; точная команда, настоящий stdout, stderr и exit code — в `checks.txt`. Дополнительно сохранены отдельные `stdout.txt` и `stderr.txt`. Код завершения **0**, stderr пустой.

Модель проверила 11 наборов: предоставленные данные; отсутствие продаж; отсутствие меток; только неактивную метку; одну активную метку; несколько активных меток; смешанные активные и неактивные метки; две одинаковые реальные продажи; одинаковые суммы у разных товаров; сочетание отсутствующей, неактивной и активных меток; десятичные, нулевые и отрицательные суммы. Во всех наборах проверены мультимножество полных строк, кратность исходных номеров строк и математическая сумма. Ожидаемые строки получены прямой проверкой «существует хотя бы одна активная метка», исправление моделировалось через множество активных товаров. На исходных данных модель соединения получила номера `[1, 1, 2, 2]` и сумму 400, модель исправления — `[1, 2]` и сумму 200. Обе рассмотренные ошибочные дедупликации дали 100.

Границы этих результатов: Python не разбирает и не исполняет текст запроса 1С. Это конечные проверки модели, а не подтверждение компиляции запроса или исполнения на всех данных. Использован Decimal для денежных значений. Пустой набор в модели имеет математическую сумму 0; поведение агрегата 1С на пустом наборе, включая NULL и форму результата, не проверено. Контракт не уточняет, требуется ли принудительная замена пустого результата на 0, поэтому дополнительное преобразование в запрос не внесено. В модели все продажи относятся к одному выбранному документу; изоляция другого документа подтверждена только статическим наличием условия по ссылке, платформенно не проверена. Срезы, периоды и левое соединение в этом задании отсутствуют.

Подготовленная процедура для тестовой базы 1С — **не выполнена**:

1. Зафиксировать версию платформы, режим совместимости, СУБД и роль. Проверить предложенный текст доступными средствами целевой платформы. Создать указанные метаданные и предоставленные записи в тестовой базе; передать ссылку документа в `&Документ`.
2. Выполнить исходный и исправленный запросы: для исходного набора ожидаются 400 и 200 соответственно. Эталон 200 обоснован реальными строками 1 и 2, независимо от ошибочного запроса.
3. Для диагностики заменить итоговую агрегацию выводом `Ссылка`, `НомерСтроки`, `Товар`, `Сумма`, сохранив источники и отборы каждого варианта. Проверить мультимножества: в исходном варианте номера 1 и 2 встречаются по два раза, в исправленном — по одному; строка 3 отсутствует. Поле `НомерСтроки` используется для проверки, добавлять его в итоговый отчёт не требуется.
4. Перенести дополнительные наборы из `verify.py`, проверить состав и кратность строк и суммы; отдельно зафиксировать фактические NULL/число строк результата на пустом наборе. Добавить второй документ с подходящей продажей и подтвердить его исключение при прежнем `&Документ`. Не сравнивать порядок строк.
5. Если нужна оценка скорости, замерить варианты на представительном объёме, с одинаковыми параметрами, правами и условиями кеша, несколькими повторными прогонами; изучить планы целевой СУБД и доступные индексы. Зафиксировать число обращений и объёмы промежуточных данных.

Неизвестные версия платформы и СУБД не мешают выявить ошибку на данных, но ограничивают подтверждение синтаксиса и стоимости. Логически исправление устраняет размножение строк перед суммированием; фактическое ускорение, план исполнения и пригодность конкретных индексов не измерялись и не обещаются. Дополнительных сведений о метаданных для установленной причины не требуется.
