# Оценка решений агента

Здесь проверяется, **что агент сделал и чем обосновал**, а не совпадение слов или заголовков. Структурная валидность скилла не оценивает его решения. [Текущий фактический отчёт](../docs/final-validation.md) отделён от этого протокола.

## Сценарии

| Скилл | Реальная проблема | Уже корректный код | Недостаточно данных |
| --- | --- | --- | --- |
| refactor | R1: [before](../examples/refactor/before.bsl), контракт и задача в [описании](../examples/refactor/README.md) | R2: [after](../examples/refactor/after.bsl), тот же контракт | R3: экспортная обёртка и запрос переноса, фрагмент в [описании](../examples/refactor/README.md) |
| debug | D1: [before](../examples/debug/before.bsl), роль вызывающего кода и контракт в [описании](../examples/debug/README.md) | D2: [after](../examples/debug/after.bsl), собственная транзакция и управляемый сбой | D3: только симптом зависимости от роли, текст в [описании](../examples/debug/README.md) |
| query-review | Q1–Q4: [исходные запросы, метаданные, записи и цели](../examples/query-review/README.md) | Q5: [correct.query](../examples/query-review/correct.query), контракт и данные в описании | Q6: две версии среза с неизвестной структурой, текст в описании |

Для каждого сценария в описании есть вход, критерии успеха, существенный результат и границы. `after` — пример допустимого решения, а не требование буквального совпадения. Q1 возвращает исходный запрос как корректное решение; Q3 зависит от явно заданной цели; R1 допускает аргументированное отсутствие полезного изменения.

## Протокол повторного прогона

1. Подготовьте отдельный временный каталог. Передайте агенту выбранный `SKILL.md`, только нужные references и **исходные** артефакты. Из описания скопируйте задачу, контракт метаданных и входные данные без разбора/ожидаемого результата. Не давайте `after`, fixtures с expected-полями, рубрику, прошлые ответы и отчёт авторской проверки при запуске проблемного сценария. При Q1 передаются обе версии, поскольку это сравнение.
2. Зафиксируйте дату, AI-инструмент, доступный идентификатор модели/настройки (если раскрыты), разрешённые инструменты и наличие 1С. Задачи не должны писать в рабочую базу. Не объясняйте агенту предполагаемую причину заранее.
3. Сохраните необработанный ответ и предложенный diff. Фактические запуски инструментов и их результаты фиксируйте отдельно от предложенной процедуры проверки. Для проверки автоматического выбора проведите **отдельный** тест без явного указания скилла; явное чтение файла его не заменяет.
4. Сопоставьте результат с рубрикой ниже. Допустимы разные формулы представления, имена внутренних функций и запросы с той же доказанной семантикой. Не используйте точный текст как критерий.
5. Отметьте `pass`, `partial`, `fail` или `not-run` по каждому пункту с объяснением и ссылкой на ответ. Не усредняйте скрытое изменение бизнес-результата с красивым отчётом. Изменение скилла делайте по продемонстрированному сбою, затем повторяйте затронутый сценарий.

Для строгого сравнения используйте свежий контекст на **каждый** сценарий и несколько прогонов. Для сравнения со стандартным обращением запустите те же входы без скилла, с теми же инструментами/моделью/лимитами, и оцените по той же рубрике. В первой версии такого эксперимента нет.

## Рубрика

| Критерий | Успех | Существенный провал |
| --- | --- | --- |
| Контракт | Использованы данные задачи; неизвестное помечено | Выдуманы метаданные, БСП, среда или результат запуска |
| Локальность | Изменение связано с причиной/структурной задачей | Переименование экспорта, расширение прав или изменение формулы без основания |
| Корректность refactor | Сохранены два округления, сигнатура, последовательное заполнение; учтена точность | Одно округление, итог вместо строки, потеря повторов или новая атомарность |
| Корректность debug | Найден путь после подавленного исключения; завершение собственной транзакции и передача сбоя | Только лог/сообщение с продолжением успеха, отмена чужой транзакции, полные права как лечение |
| Корректность query | Доказаны конкретные строки/кратность, цель исправления ясна | «Всегда перенести отбор», `SUM DISTINCT` как общее лечение, потеря отсутствующих/повторных строк |
| Корректный вход | Возможен обоснованный ответ без изменений | Искусственный дефект или ненужная архитектурная переделка |
| Неполный вход | Условный вывод и следующий влияющий вопрос | Категоричная причина без свидетельств или требование всех материалов сразу |
| Проверки | Сценарии и эффекты проверяемы; фактическое отделено от планируемого | Модель названа запуском 1С, структурный валидатор — доказательством качества агента |

Ответы ограниченного первого прогона сохранены в [results](results/README.md). Оценка автором проекта не является независимой экспертной сертификацией.

Новые независимые прогоны Q2–Q4 и повтор Q4: [ответы, редакции и оценка](query-forward/README.md). Отдельные фактические исполнения на учебной платформе: [протокол 1С](platform/README.md).
