# Запросы: шесть сценариев и пять механизмов

Все объекты и данные придуманы специально для проекта. `.query` — текст языка запросов 1С, не SQL СУБД. Для ревью передавать агенту только указанные исходные материалы и контракт. Файлы `after` и ожидаемые результаты предназначены проверяющему. Исходные данные находятся в `fixtures.json`; строки сравниваются без порядка, если он не задан.

## Q1 — перенос отбора в СрезПоследних

Запрос: «Проверь эквивалентность предложенной оптимизации». Материалы: `slice-last/original.query`, `slice-last/proposed.query`, структура и записи ниже.

Независимый периодический регистр сведений `УчебныеЦены`, периодичность — секунда, не подчинён регистратору. Единственное **измерение** `Товар` — Строка(20). **Реквизит** `Источник` — Строка(20). **Ресурс** `Цена` — Число(15,2). Поле `Период` стандартное. Активность записей подчинённого регистра не используется. `&Дата = 03.01.2026 00:00:00`, `&Источник = "ручной"`.

| Период | Товар | Источник (реквизит) | Цена |
| --- | --- | --- | --- |
| 01.01.2026 | A | ручной | 10 |
| 02.01.2026 | A | импорт | 12 |
| 01.01.2026 | B | ручной | 20 |

Контракт: получить последние цены **в целом** на дату и оставить только товары, у которых источник именно последней цены ручной. Ожидается только `(B, 20)`. В предложении получается `(A, 10), (B, 20)`: отбор выполнен до выбора последней записи. Исправление для заданного контракта — сохранить `original.query`. Если бизнесу нужна «последняя ручная цена», верен предложенный вариант, но это другая задача.

Критерии: агент различает реквизит и измерение, объясняет расхождение на A, не обещает ускорение, сохраняет исходный запрос как решение для данного контракта. Дополнительные проверки: дата до первой записи, точно в момент второй, после второй; товар без записей; если `Источник` сделать измерением — заново вывести семантику для нового ключа, не повторять прежний вывод автоматически.

## Q2 — соединение завышает сумму

Запрос: «В отчёте задваиваются суммы. Исправь запрос». Материалы: `join-multiplication/before.query`, `joins` из fixtures и структура.

Учебный документ `УчебнаяПродажа`, табличная часть `Товары`: стандартные `Ссылка`, `НомерСтроки`; реквизиты `Товар` Строка(20), `Сумма` Число(15,2). Независимый непериодический регистр `УчебныеМетки`: измерения `Товар` Строка(20) и `Метка` Строка(20), ресурс `Активна` Булево. Ключ `(Товар, Метка)` уникален, товар сам по себе не уникален. `&Документ` — ссылка на выбранный учебный документ; все продажи fixtures относятся к нему.

Контракт: сумма продаж документа для товаров, у которых есть хотя бы одна активная метка. Две настоящие строки A по 100 и две метки A дают ошибочные 400. Правильный результат 200. Продажа B на 50 исключается: активной метки нет. `after.query` использует вхождение, сохраняя две исходные продажи.

Критерии: агент доказывает размножение, сохраняет законные повторы, не исправляет сумму через `СУММА(РАЗЛИЧНЫЕ ...)` (получилось бы 100). Сравнивать с требованием 200, а не со старым итогом 400. Дополнительно: нет меток, одна, две; повторная реальная продажа; пустой документ. Для агрегата на пустом наборе отдельно проверить представление результата платформой; модель суммы Python/SQLite не подтверждает его.

## Q3 — отбор после левого соединения

Запрос: «Нужно вывести все товары, добавив комментарий только активного разрешения. Проверь запрос». Материалы: `left-join/before.query`, `left_join` из fixtures.

Справочник `УчебныеТовары` непериодический, неиерархический, содержит элементы A, B, C. Независимый непериодический регистр `УчебныеРазрешения`: единственное измерение `Товар` типа СправочникСсылка.УчебныеТовары; ресурс `Активна` Булево; реквизит `Комментарий` Строка(100). Не более одной записи на товар. A — активен, B — неактивен, C — записи нет.

Исходный результат: только A. Требуемый: A с комментарием, B и C с `NULL`. `after.query` переносит условие активности в `ПО`. Вариант `ГДЕ Активна = ИСТИНА ИЛИ Товар ЕСТЬ NULL` не возвращает B и не решает задачу.

Критерии: объяснена потеря строк и связь с контрактом. Если изменить требование на «только товары с активным разрешением», исходный запрос корректен по результату. Левое соединение само по себе не дефект. Проверить активную, неактивную, отсутствующую запись и отсутствие размножения по ключу.

## Q4 — пакетирование запроса в цикле

Запрос: «Уменьши число запросов, сохранив результат по каждой строке». Материалы: `query-in-loop/before.bsl`, раздел `batch` fixtures, контракт ниже.

Независимый **непериодический** регистр `УчебныеФиксированныеЦены`: единственное измерение `Товар` Строка(20), ресурс `Цена` Число(15,2). Один товар — не более одной цены. Серверный общий модуль, «Сервер» включено, «Вызов сервера» выключено. `Строки` — ТаблицаЗначений: `ИдентификаторСтроки` Число(10,0), `Товар` Строка(20), `Цена` Число(15,2), `ЕстьЦена` Булево. Идентификаторы уникальны; порядок строк значим. Цены и доступность записей **не меняются в течение операции**, между итерациями нет записей. Входы корректны, чтение разрешено. Эквивалентность при исключениях чтения и конкурентном изменении не обещается: пакетная версия читает до заполнения строк, старая могла уже заполнить часть строк.

Для A, B, A, C, Z ожидаются пять строк с прежними идентификаторами: 10, 20, 10, отсутствующая цена, настоящая нулевая цена. Отсутствие обозначается `Цена=0, ЕстьЦена=Ложь`; нулевая цена — `Цена=0, ЕстьЦена=Истина`. Решение `after.bsl` помещает исходные идентификаторы и товары во временную таблицу, сопоставляет цены левым соединением и заполняет исходные строки через соответствие **по идентификатору строки**; повторы и порядок сохраняются. Пакет из двух операторов выполняется одним вызовом `Запрос.Выполнить()`. Пустой вход не выполняет запрос.

Платформенная проверка выявила ошибку прежнего `after.bsl`: при цене для `A` исходный запрос находил её также для `a` и `A `, а восстановление по строковому ключу товара теряло соответствие. Новый вариант оставляет сравнение товаров языку запросов. [Неудачный прогон и повторная проверка](../../evals/platform/README.md) сохранены отдельно; математическая модель с точным равенством строк такого различия не проверяет.

Критерии: не теряются повтор A, C и нулевая цена Z; не утверждается универсальное пакетирование по одному товару при других датах/складах. Число явных `Запрос.Выполнить()` для непустого набора снижается с N до 1 по структуре кода; фактическое время не измерено. Для больших наборов возможны пакеты, но их размер требует измерений. Проверить пустой список, один элемент, повторы, отсутствие всех цен. В варианте с записью между итерациями или меняющимися ценами сначала пересмотреть контракт, а не обещать эквивалентность.

## Q5 — корректный запрос

Запрос: «Проверь `correct.query`». Структура документа как в Q2; задача — сумма всех строк выбранного документа по товару, включая реальные повторы. Данные `joins.sales`: ожидается `(A, 200), (B, 50)`.

Критерии: агент признаёт соответствие заданному контракту, не добавляет `РАЗЛИЧНЫЕ`, соединение или индекс без доказанной потребности. Отсутствие `УПОРЯДОЧИТЬ ПО` допустимо: порядок не задан. Обоснованное отсутствие замечаний — успешное ревью, а фактический план/время остаются непроверенными.

## Q6 — недостаточно данных

Материалы: только два текста Q1 с именем регистра `ЦеныПользователя`; структура и ожидаемая семантика неизвестны. Запрос: «Можно перенести отбор по Источнику внутрь среза?»

Критерии: агент показывает условный риск и запрашивает, чем является `Источник` (измерение, реквизит, ресурс), полный ключ и какой результат нужен. Не утверждает неизбежное расхождение для всех регистров и не требует вторую версию — она уже дана. Статический разбор доступен без базы.

## Как проверить в 1С

В отдельной учебной конфигурации создать только объекты выбранного кейса с описанной структурой. Для Q2/Q5 заполнить один документ без проведения; для регистров записать перечисленные строки штатным редактором или локальной учебной обработкой. Для Q3 использовать реальные ссылки созданных A/B/C, а не строки из JSON. Выполнить тексты через доступную в проекте консоль запросов либо объект `Запрос` на сервере, установив параметры правильных типов. Наличие консоли проект не предполагает.

Сравнить значения и кратность с fixtures. Для Q4 по очереди поместить before/after в тестовый серверный модуль, вызвать `ЗаполнитьЦены` на свежих копиях таблицы, сверить все пять строк и флаг наличия. Проверить серверный синтаксис, версию платформы, совместимость, роль, периодичность/ключи. Не выполнять учебные записи в рабочей базе.

Тесты Python проверяют арифметику и реляционные контрпримеры; они не компилируют язык запросов 1С, не воспроизводят СУБД 1С, RLS, СКД или виртуальные таблицы платформы. Отдельно выполнены ограниченные проверки Q1–Q5 на учебной 1С 8.5.1.1150: [протокол](../../evals/platform/README.md). Перечень фактически исполненных случаев не следует расширять на все возможные данные или версии.
